[Quick start](/quick-start) gets a chat on screen in one go. This page takes
the same result apart and rebuilds it in four stages, so you can see what each
primitive contributes and where your own code belongs.

The first three stages run on static data and local state — copy any of them and
they work immediately. The fourth connects a real model.

## 1. Render a thread

`Thread` is a scroll container with opinions about one thing: staying at the
bottom. It follows new content while you're already there and releases the moment
you scroll away, so a stream never yanks the page out from under you.

<Demo component={<ThreadStage />} file="build-a-chat/demos/thread.tsx" />

`Thread.Viewport` is the scrolling element and `Thread.Content` is the column
inside it. Neither sets width, spacing, or colour. The viewport does need a
definite height, here `h-full` inside a sized root, because its content cannot
size it. At this stage the rows are plain paragraphs, so the thread uses
`autoScroll="bottom"`, which lands each new row at the bottom and needs no turns.

## 2. Add messages

`Message.Root` renders a `div` carrying `data-role`, `data-last`, and
`data-error`, and nothing else. No bubble, no avatar, no alignment: the role is
reported, and you decide what it looks like.

<Demo component={<MessagesStage />} file="build-a-chat/demos/messages.tsx" />

The bubble is styled by reading `data-role` through a Tailwind group on the root,
which is why the same `Message.Text` element renders as a card for the user and
as bare text for the assistant. `role` is an opaque string — the package never
enumerates the set, so `"system"` or `"tool"` work the same way.

## 3. Wire the composer

Sending from `Composer.Root` clears the draft and hands you a
`ComposerSubmitData`; appending the turn is your call.

<Demo component={<ComposerStage />} file="build-a-chat/demos/composer.tsx" />

Inside `Thread.Composer`, the thread measures the composer and publishes the
room it takes as `--thread-inset-bottom`. The rest of the layout is yours. The
slot sits at `absolute inset-x-0 bottom-0`, and `Thread.Content` pads its bottom
with `pb-(--thread-inset-bottom)`, so messages scroll under the input but never
end behind it, at any composer height.

This stage also switches to the default `autoScroll="follow"`, where a new turn
lands at the top of the viewport. Each question and its reply share one
`Message.Turn`, and the last turn takes `min-height: var(--thread-turn-min-height)`
from a rule on `Thread.Content`. [Thread](/primitives/thread#spacing-a-landed-turn)
explains how that height lines up with the padding.

At this point everything is local: submitting appends a message, and no request
leaves the page.

## 4. Stream responses

This stage has no live demo. Docs pages here never call a model, so what follows
is the wiring, shown as code rather than run.

Swap local state for `useChat`, which owns the message list and the request:

```tsx
"use client";

import { useChat } from "@ai-sdk/react";
import type { AttachmentItem } from "@intentface/ui/attachments";
import { Composer, type ComposerSubmitData } from "@intentface/ui/composer";
import type { FileUIPart } from "ai";

export function Chat() {
  const { messages, sendMessage, status, stop } = useChat();

  const handleSubmit = async (data: ComposerSubmitData) => {
    if (data.kind !== "message") return;
    // The composer revokes the blob URLs once onSubmit settles, so read them first.
    const files = await Promise.all(data.files.map(toFilePart));
    sendMessage({ text: data.text, files });
  };

  return (
    <Composer.Root onSubmit={handleSubmit}>
      {/* … the same tree as stage 3 … */}
      <Composer.Submit
        isGenerating={status === "submitted" || status === "streaming"}
        onStop={stop}
      />
    </Composer.Root>
  );
}

const toFilePart = async (item: AttachmentItem): Promise<FileUIPart> => {
  const blob = await (await fetch(item.url)).blob();
  const url = await new Promise<string>((resolve, reject) => {
    const reader = new FileReader();
    reader.onload = () => resolve(String(reader.result));
    reader.onerror = () => reject(reader.error);
    reader.readAsDataURL(blob);
  });
  return { type: "file", url, mediaType: item.mediaType ?? blob.type, filename: item.filename };
};
```

`useChat` reports `"submitted"` from the send until the reply starts, and
`"streaming"` while it arrives, so pass both as `isGenerating`. Otherwise the
button offers send, not stop, while the request is already in flight. While
generating, `Composer.Submit` calls `onStop` instead of sending and changes its
label from "Send message" to "Stop generating", so send-to-stop needs no
branching of your own.

By default a composer attachment's `url` is a `blob:` URL that only this page
can read, so `toFilePart` turns each one into a data URL the server can decode.

`messages` from `useChat` are `UIMessage`s, which satisfy this package's
[`ChatMessage`](/reference/types#chatmessage) contract structurally, so they
render through `Message` with no adapter. A `UIMessage` keeps its text in
`parts`, so stage 3's `{message.text}` becomes the message's text parts, picked
out with `isTextPart` from `@intentface/ui/types`:

```tsx
{message.parts.filter(isTextPart).map((part, index) => (
  <Message.Text key={index}>{part.text}</Message.Text>
))}
```

The route is the standard AI SDK handler — nothing in this package is involved:

```ts
// app/api/chat/route.ts
import { openai } from "@ai-sdk/openai";
import { convertToModelMessages, streamText, type UIMessage } from "ai";

export async function POST(req: Request) {
  const { messages }: { messages: UIMessage[] } = await req.json();

  const result = streamText({
    model: openai("gpt-5"),
    messages: await convertToModelMessages(messages),
  });

  return result.toUIMessageStreamResponse();
}
```
