## Usage guidelines

- **Scroll surface** — lands the newest turn, follows the stream while you're at the bottom, and yields the moment you scroll up.
- **Auto-scroll modes** — `off` / `bottom` / `jump` / `follow` via the `autoScroll` prop (see below).
- **The layout is yours** — the thread measures and publishes CSS variables, and applies none of the layout. You position the composer, size the viewport, pad `Thread.Content` and give the last turn its `min-height`, as [Spacing a landed turn](#spacing-a-landed-turn) explains.
- **The viewport needs a definite height** — `Thread.Viewport` is a size container, so its content cannot size it and a viewport sized only by `max-height` collapses. Give it `h-full` inside a sized root.
- **Children are turns** — in `"follow"` and `"jump"` the last child of `Thread.Content` lands at the top, so a reply on its own row pushes its question out of view. Wrap each question and its reply in one `Message.Turn` with nothing after the last, or use `autoScroll="bottom"` for a flat transcript.
- **Owns no data** — you map your messages in; rows are addressable by a `data-message-id` attribute.
- **Cheap while streaming** — no scroll handler and no re-render per token; see [Why the scroll subsystem is cheap](#why-the-scroll-subsystem-is-cheap).
- **Get started** — see [Quick start](/quick-start) to add the package.

## Anatomy

```tsx
<Thread.Root>
  <Thread.Viewport>
    <Thread.Content />
  </Thread.Viewport>
  <Thread.Composer />
</Thread.Root>
```

A realistic thread. Every layout class is yours, because the package applies
none: the composer's position, the viewport's height, the padding and the last
turn's `min-height`. The fade and the scroll button are optional and not parts:

```tsx
<Thread.Root className="relative h-full [--thread-inset-top:1rem] [--thread-composer-gap:2rem]">
  <div aria-hidden className="pointer-events-none absolute inset-x-0 top-0 z-1 h-(--thread-inset-top) bg-linear-to-b from-white to-transparent" />
  <Thread.Viewport className="h-full">
    <Thread.Content className="flex flex-col gap-4 px-4 pt-(--thread-inset-top) pb-(--thread-inset-bottom) [&>*:last-child]:min-h-(--thread-turn-min-height)">
      {turns.map((turn) => (
        <Message.Turn key={turn.key} data-message-id={turn.key}>{/* question, then reply */}</Message.Turn>
      ))}
    </Thread.Content>
  </Thread.Viewport>
  <Thread.Composer className="absolute inset-x-0 bottom-0">
    <Composer.Root onSubmit={sendMessage}>{/* … */}</Composer.Root>
  </Thread.Composer>
  {/* Built from `useThread()`'s `isAtBottom` and `scrollToBottom`. */}
  <ScrollToBottomButton />
</Thread.Root>
```

## Examples

### Choosing an auto-scroll mode

`autoScroll` decides two things at once: where a new turn lands, and whether the
view keeps following while text streams into it. `"follow"` and `"jump"` land a
turn by scrolling to the bottom, so the newest turn reaches the top only when it
is tall enough. [Spacing a landed turn](#spacing-a-landed-turn) shows the
`min-height` that gives it that height.

export const autoScrollModes = [
  { value: '"follow"', default: true, description: "Newest lands at the top; the view follows the stream (ChatGPT-style)." },
  { value: '"bottom"', description: "Newest lands at the bottom; the view follows the stream (Codex-style)." },
  { value: '"jump"', description: "Newest lands at the top; the view does not follow." },
  { value: '"off"', description: "A plain scroll area with no landing and no follow." },
];

### Opening position

Where a saved transcript opens is a consequence of the mode — there is no
separate `defaultScrollPosition` prop. `"bottom"` opens at the end; `"follow"`
and `"jump"` open with the newest turn's top at the top inset (the last turn's
`min-height` does this); `"off"` opens at the start. To deep-link into the
middle of a transcript, call `scrollToMessage` on mount — it queues until the
rows exist and overrides the landing.

The follow is released by deliberate upward reading intent and re-arms when you
return to the bottom (see [Keyboard](#keyboard)). Content growth alone never
releases it: a large code block landing at once won't drop the follow
mid-stream. Once you scroll up, the follow can't scroll again until you return
to the bottom.

### Spacing a landed turn

Set `--thread-inset-top` on `Thread.Root` for the space above a turn once it
lands, and `--thread-composer-gap` for the room between the last line and the
composer. Both default to 0. A turn lands exactly `--thread-inset-top` from
the top only while three values agree:

- **The top padding is `--thread-inset-top`.** Put `pt-(--thread-inset-top)`
  on `Thread.Content`.
- **The bottom padding is `--thread-inset-bottom`.** `Thread.Composer` writes its
  distance from the root's bottom edge, plus `--thread-composer-gap`, to that
  variable. Put `pb-(--thread-inset-bottom)` on `Thread.Content`. Without a
  `Thread.Composer`, nothing writes it, so set it on `Thread.Root` if the
  transcript needs space at the bottom.
- **The last turn's `min-height` is `--thread-turn-min-height`.** In `"follow"`
  and `"jump"` the root publishes the viewport's height minus both paddings, so
  the last turn fills the view between them when scrolled to the bottom. In
  `"bottom"` and `"off"` it publishes `0px`, so the rule can stay on
  `Thread.Content` in every mode.

Any other padding, or a margin between the viewport and the turns, shifts the
landing by its own size. Leave the `min-height` rule out and `"follow"` and
`"jump"` land at the bottom like `"bottom"`, which can be a deliberate choice.

The top inset and the `gap-*` between turns are independent. When the landing
gap is larger, the end of the previous turn shows above a landed turn, by the
top inset minus the spacing. Cover it with a top fade, or keep the top inset
at or below the spacing.

### Fading the edges

A fade is your own `div` inside `Thread.Root`, absolute, `aria-hidden` and
`pointer-events-none`. Size the top one with `h-(--thread-inset-top)` and the
bottom one with `h-(--thread-inset-bottom)`, and give a header that floats over
the top the same height as the top inset.

```tsx
<Thread.Root className="relative h-full [--thread-inset-top:1rem] [--thread-composer-gap:2rem]">
  <div aria-hidden className="pointer-events-none absolute inset-x-0 top-0 z-1 h-(--thread-inset-top) bg-linear-to-b from-white to-transparent" />
  <Thread.Viewport className="h-full">{/* … */}</Thread.Viewport>
  <div aria-hidden className="pointer-events-none absolute inset-x-0 bottom-0 z-1 h-(--thread-inset-bottom) bg-linear-to-t from-white to-transparent" />
  {/* Above the bottom fade, so the composer stays sharp. */}
  <Thread.Composer className="absolute inset-x-0 bottom-0 z-2">{/* … */}</Thread.Composer>
</Thread.Root>
```

### Laying out without Tailwind

Plain CSS needs the same rules, and the parts' data attributes are the
selectors. Give the last turn `box-sizing: border-box` if it has padding or a
border, otherwise its `min-height` excludes them and the turn lands short of
the top.

```css
[data-thread-root] {
  height: 100%;
  --thread-inset-top: 1rem;
  --thread-composer-gap: 2rem;
}

[data-thread-scroller] {
  height: 100%;
}

[data-thread-content] {
  display: flex;
  flex-direction: column;
  gap: 1rem;
  padding-inline: 1rem;
  padding-top: var(--thread-inset-top);
  padding-bottom: var(--thread-inset-bottom, 0px);
}

/* 0px outside "follow" and "jump", so the rule can stay in every mode. */
[data-thread-content] > :last-child {
  box-sizing: border-box;
  min-height: var(--thread-turn-min-height);
}

[data-thread-composer] {
  position: absolute;
  inset-inline: 0;
  bottom: 0;
}

/* Your own fade over the top inset. Optional. */
[data-slot="thread-fade"] {
  position: absolute;
  inset-inline: 0;
  top: 0;
  z-index: 1;
  height: var(--thread-inset-top);
  background: linear-gradient(to bottom, white, transparent);
  pointer-events: none;
}
```

### Jumping to a message

`scrollToMessage` finds a row by the `data-message-id` attribute you put on it.
There is no wrapper part and no registry: rows resolve lazily at call time, so a
long transcript adds no per-row setup, only the lookup when you jump.
`useThreadVisibility` reads the same attribute to report which rows are on
screen, and creates its observers only once something subscribes.

Only the thread's own viewport scrolls, so a thread embedded in a scrolling page
never moves the page. Where the row lands follows the same CSS as the browser's
own scroll-into-view: `scroll-padding` on `Thread.Viewport` keeps room at its
edges (lengths or percentages of its height), and `scroll-margin` on a row adds
room around that row. To land rows clear of the top fade and the composer, pad
the viewport by the insets:

```tsx
<Thread.Viewport className="scroll-pt-(--thread-inset-top) scroll-pb-(--thread-inset-bottom)">
```

### Timing the scroll

Smooth scrolls are the browser's own until you give them a timing. Set one on
the root and the thread animates them itself — the landing, `scrollToBottom`,
`scrollToTop` and `scrollToMessage` — and pins the follow:

```css
[data-thread-root] {
  --thread-scroll: 450ms cubic-bezier(0.2, 0.8, 0.2, 1);
}
```

The value reads like `transition`: a duration, then any CSS easing, `linear()`
included. That makes a Motion spring a one-liner, since `spring()` prints
exactly that pair:

```tsx
import { spring } from "motion";

<Thread.Root style={{ "--thread-scroll": String(spring(0.5, 0)) }}>{/* … */}</Thread.Root>
```

Keep `bounce` at 0: the scroller can't move past its end, so an overshoot at
the bottom is clipped into a hard stop.

`autoScroll` decides which scrolls happen; the timing only shapes the ones that
animate. The follow never does: a reply grows a line at a time, so pinning
reads as smooth already, while an animated follow would keep a frame loop on
the main thread for the whole stream and trail the newest text.

The timing is one set of values for every scroll, so set it once and leave it.
Swapping it from a selector does nothing, because the thread reads it before
any attribute changes, and it would cost a restyle of every message, because
custom properties inherit.

To pace by distance instead, set `--thread-scroll-speed` in pixels per second;
a duration set alongside it becomes the cap. `--thread-scroll: none` opts a
thread back into the native smooth scroll, over any longhand — useful when a
shared stylesheet sets a timing for every thread.

While an animation runs, the root carries `data-scrolling`, naming why it
started: `land`, `bottom`, `top` or `message`. Use it for styling, such as
hiding the scroll button mid-flight.

The destination is re-read every frame, so a reply that starts streaming before
the landing finishes is carried along by it instead of restarting it. In
`"jump"` the landing's destination is fixed when it starts: a reply outgrowing
the reserve mid-flight never turns the landing into a follow. Any wheel, touch,
scroll key or scrollbar press stops the animation where it is, and under
`prefers-reduced-motion` every scroll is instant.

## Why the scroll subsystem is cheap

Thread's scroll subsystem is built to stay out of the way while a reply streams:
the work it does is event-driven and small, not per token or per frame.

- **No scroll handler.** Edge detection is an IntersectionObserver sentinel per
  edge, computed off the main thread. Scrolling runs zero JavaScript.
- **Landing and follow are event-driven** — a MutationObserver for new turns, a
  ResizeObserver for growth, one `scrollTo` per change. No per-token geometry
  reads, no animation-frame polling.
- **A timed scroll costs one frame loop, only while it runs.** With
  `--thread-scroll` set, each smooth scroll reads its timing once and then does
  one `scrollTo` per frame until it ends. Unlike the native smooth scroll, it
  runs on the main thread, so a frame lost to heavy rendering is a frame the
  scroll skips. The follow never starts one, because a timed thread pins it.
  Leave the timing unset to keep the native scroll.
- **Edge state lives in external stores** (one per edge), so a flip re-renders
  only the components that read it (your scroll button) — never the Thread tree.
- **Lazy capabilities cost nothing until used**: visibility tracking creates its
  observers on the first `useThreadVisibility` subscriber and tears them down
  with the last; the prepend-preservation scroll listener exists only when
  `preserveScrollOnPrepend` is set.

The boundary: Thread does not virtualize. Cost is O(rendered rows) of DOM, which
holds comfortably for realistic transcripts (hundreds to low thousands of
turns). What re-renders during a stream is decided by your message components —
see [Why the composer needs isolating](/primitives/composer#why-the-composer-needs-isolating).

## Keyboard

The viewport carries `tabIndex=0`, so keyboard users can Tab to it and scroll
with the usual keys. Scrolling is otherwise native — the thread intercepts only
the upward keys, `ArrowUp`, `PageUp` and `Home`, which release auto-follow.
Scrolling down never releases it: doing so at the bottom would leave the view
unfollowed while pinned there.

An upward wheel or a downward touch-drag releases follow the same way; a
scrollbar drag away from the bottom releases it via the sentinel.

### Thread.Viewport

The scroll container. It sets `overflow-y: auto`, `overflow-x: hidden` and
`container-type: size` inline, so `100cqh` inside it is its height. A size
container ignores its content's height, so give it a definite height, such as
`h-full` in a sized root. Focusable so keyboard users can scroll it.

### Thread.Composer

A slot for the composer, with no positioning of its own. A `ResizeObserver`
measures its border box, including when it mounts, remounts or unmounts, and
writes `--thread-inset-bottom`, `--thread-composer-height` and `--thread-composer-width`
on `Thread.Root`. It removes all three when it unmounts. Renders
`data-thread-composer`.

Position it yourself, such as with `absolute inset-x-0 bottom-0`, so the content
scrolls under it. Anything inside it that should not add to the inset, such as a
floating scroll button or an overlay panel, has to be absolute or portaled like
`Composer.Panel`'s default. An in-flow `Composer.Panel` (`anchor={false}`) is
part of the slot, so `--thread-inset-bottom` grows to include it.

## useThread

Read the scroll state and issue commands from anywhere inside `<Thread.Root>`:

There is no scroll-to-bottom part. Build one from `isAtBottom` and
`scrollToBottom`:

```tsx
const { isAtBottom, scrollToBottom } = useThread();

return isAtBottom ? null : (
  <button type="button" onClick={() => scrollToBottom()} aria-label="Scroll to latest">
    <ArrowDownIcon />
  </button>
);
```

`scrollToMessage` resolves rows lazily by the `data-message-id` attribute — put
it on each row you want addressable; there is no wrapper component and no
per-row cost:

```tsx
{turns.map((turn) => (
  <Message.Turn key={turn.key} data-message-id={turn.key}>{/* … */}</Message.Turn>
))}
```

## useThreadVisibility

Track which rows are in view — e.g. to highlight the active turn in an outline.
Subscribing lazily creates the tracking observers; when the last subscriber
unmounts they are torn down, so threads that never call it pay nothing. Rows
are identified by the same `data-message-id` attribute `scrollToMessage` uses.
